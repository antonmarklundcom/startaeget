# B1 — Blog admin

## Built
- `/admin/` — git-backed editor for every article in `content/articles/**`: list (hub filter, title/slug search, state chip), `/admin/ny/` for a blog post, `/admin/artiklar/[hub]/[slug]/` editor, delete. No site header or footer, `src/styles/admin.css` only, `force-dynamic` + `robots: noindex` on every screen.
- Auth: `ADMIN_PASSWORD` compared with `crypto.timingSafeEqual`, session = HMAC-SHA256 over `expires.nonce` in an httpOnly cookie (7 days, `sameSite: lax`, `secure` in production, path `/admin`), 5 *failed* logins per IP per 15 min → the login screen refuses. No JWT library, no DB, no user table.
- `src/middleware.ts` guards `/admin/*` (Web Crypto, Edge runtime) and the authed layout re-checks in Node; both accept exactly the same tokens (asserted in `tests/admin.spec.ts`).
- `src/lib/admin/store.ts` — one interface, two backends: `github` (Contents API on `GITHUB_BRANCH`, read = the branch, write = PUT with the file's sha, commit `admin: <title>`, 60 s cache) when `GITHUB_TOKEN` + `GITHUB_REPO` are set, else `local` (`content/` on disk). All HTTP lives in `src/lib/admin/github.ts`.
- Validation gate in front of *both* backends: `articleFrontmatterSchema` + MDX compile + repeated-heading check + slug collision (hub, reserved route, any other article/page/lead magnet) + internal-link resolution as a warning. An invalid file is never written anywhere.
- Editor: every frontmatter field as a control (`legacy` read-only, `updated` defaults to today on save, `sources`/`faq` repeatable, `partners`/`related` multi-select from the loaders), plain textarea + toolbar (searchable link picker inserting `[text](/slug/)`, Callout, Checklist, Stat), preview compiled with the site's own `Mdx` components.
- Hub `blogg` (7th `HUBS` entry, tint sand, footer "Guider" item) and article type `post`; one real seed post, `content/articles/blogg/nystartad-sajt.mdx`.
- Lead magnets reachable at last: `content/lead-magnets/*.mdx` load through the page loader, so `/affarsplan-mall/` and `/startkostnads-checklista/` render, sit in the sitemap and are gated by `NewsletterGate` (client state only).
- `<Stat k="…" />` renders a constant from `src/lib/tax/constants.ts` with its source link and its `verifiera` flag; used in the seed post.
- `tests/admin.e2e.mjs` (login, create, link picker, preview, save, two refused saves, 375 px overflow, delete) and `tests/admin.spec.ts` (26 cases: frontmatter round-trip, validation gate, sessions in both runtimes, login throttling, the GitHub backend against a stubbed `fetch`).

## Decisions
- **Lead magnets are page-shaped, so they load through `getAllPages()`** instead of getting their own route, loader and sitemap branch. `gate: newsletter` is one optional field on `pageFrontmatterSchema`; `/[slug]/`, `sitemap.ts`, `generateStaticParams` and `scripts/expected-urls.ts` needed no change at all — which also kept B1 out of files it does not own.
- **The gate hides the body with client state and ships it in the HTML anyway** (plan §5.5: the value is the list, not the secret). That keeps the `h1`, the metadata and the printable body indexable, which is why the two pages belong in the sitemap — and why there is an honest "Visa utan att prenumerera" button rather than a fake lock.
- **The session is verified twice, in two crypto APIs.** Middleware runs on the Edge runtime where `node:crypto` does not exist, so `session-edge.ts` uses `crypto.subtle.verify` and `session.ts` uses `createHmac` + `timingSafeEqual`; a unit test pins them to the same accept/reject set. A forged cookie therefore never reaches a page that reads content.
- **Failed logins are counted by the admin's own limiter, not `src/lib/rate-limit.ts`.** That limiter charges every call, and a correct password must never spend one of the five tries.
- **The preview returns a rendered server component, not an HTML string.** Next refuses `react-dom/server` inside a server action ("render or return the content directly as a Server Component instead") — the build fails on the import. Returning the compiled node through the action reply gives the same preview with no `dangerouslySetInnerHTML`.
- **The slug is read-only when editing.** The slug is the file name; renaming would mean a write plus a delete, with a half-done state if the second call fails. Creating the new post and deleting the old one is the same work, visibly.
- **The state chip claims nothing it cannot check.** Without `NEXT_PUBLIC_BUILD_SHA` there is no way to know whether a file is live, so the Status column says "—" instead of "publicerad" (§4.16). With it, the file's blob sha on the branch is compared against the same path in the build's tree — one API call for the whole list.
- **The store is the only module that knows where a file lives**, and the validation gate sits inside its shared write path, so neither backend can skip it and no screen can write around it.

## Known issues
- The hub head panel counts blog posts as "1 guide": `HubTemplate` (D1's file, outside B1's Owns) has one noun pair for hubs and one for `/jamfor/`. One `kind`-aware label would fix it — S9 or a later `src/**` phase.
- Plan §7 items 10–12 are still open human input: `ADMIN_PASSWORD`, `ADMIN_SESSION_SECRET`, a fine-grained `GITHUB_TOKEN` (Contents: read/write), and confirmation that the Hostinger slot auto-deploys on push. Without the token the production admin writes to the slot's own disk, where the next deploy overwrites it — the top bar says "sparar lokalt" so this is visible, not silent. Whether auto-deploy is on could not be checked from the sandbox.
- `NEXT_PUBLIC_BUILD_SHA` has to be written by the build command (`NEXT_PUBLIC_BUILD_SHA=$(git rev-parse HEAD)`); nothing in the repo can set it for Hostinger.
- The github backend is covered by unit tests against a stubbed `fetch`, not against the real API: the sandbox has no token, and `api.github.com` is not reachable from it either. The local backend is what `tests/admin.e2e.mjs` drives in a browser.
- A save races nothing on disk, but in github mode two editors on the same file are resolved by GitHub's stale-sha 409 — the admin shows GitHub's own message and keeps the draft in the form. There is no merge UI, and for one admin there does not need to be.
- `src/lib/content/README.md` (O1's file, outside B1's Owns) does not yet mention `content/lead-magnets/`, the `gate` field, `type: post`, the `blogg` hub or `<Stat k>`. The schemas are the contract and they are current; the prose is one phase behind. A `src/**`-owning phase should fold it in.
- `related` and `partners` are checkbox lists over every article and partner (52 and 27 today). Fine at this size, cramped at three times it.
